# 多智能体协作的四种常见模式

多智能体系统不是“模型越多越好”。真正决定效果的是：职责是否清晰、中间产物是否可检查、失败时能不能降级。

## 1. 串行流水线（Sequential）

最常见的模式：研究员 → 写作 → 评审。前一个 Agent 的输出是后一个 Agent 的显式输入。优点是数据流单向、容易调试、容易做单元测试；缺点是总延迟是各阶段之和。

适合：调研报告、竞品分析、技术方案、内容生产。

## 2. 并行分工（Parallel）

把一个大任务拆成互不依赖的子任务，多个 Agent 同时执行，最后汇总。例如同时分析市场、技术、政策三个维度。优点是延迟低；缺点是需要处理结果冲突和汇总质量。

适合：多维度扫描、批量信息抽取、多个候选方案的独立评估。

## 3. 层级协作（Hierarchical）

一个 Manager Agent 负责拆解任务、分配角色、检查结果，其他 Agent 执行。它比串行更灵活，但调试难度更高，容易出现“管理者空转”或无限委派。

适合：任务边界不清、需要动态选择工具的复杂项目。生产环境要设置最大轮次、超时和预算。

## 4. 辩论 / 评审（Debate / Review）

多个 Agent 从不同立场生成观点，再由评审 Agent 汇总。它能暴露盲点，但成本高，而且可能强化错误共识。建议只在高质量要求、可接受高延迟的场景使用。

## 工程上最重要的三件事

1. **显式中间产物**：研究简报、提纲、引用列表都应该是结构化文本，而不是藏在对话历史里。
2. **可观测**：记录每个阶段的输入摘要、耗时、token、失败原因；否则很难定位问题。
3. **可降级**：检索失败时仍能生成报告；模型失败时能切换备用模型；PDF 失败不影响 Markdown 保存。

## 本项目的选择

ResearchCrew 默认采用“研究员 → 写作”的串行流水线。研究阶段只推送阶段事件，写作阶段才把 token 增量转发给客户端。这样既保留了过程可见性，又不会把研究笔记混进最终报告。
